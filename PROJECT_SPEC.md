# Adaptive AI-Driven Network Intrusion Detection System (NIDS)
**Document:** Project specification
**Contract version:** 1.0.0
**API base path:** `/api/v1`
**Status:** Architecture specified; implementation and experimental results not yet verified

## 1. Purpose and scope

Build an offline-first application for importing network-traffic artifacts, validating and extracting features, classifying known attack categories, flagging anomalous or novel-looking observations, assigning risk and severity, and supporting analyst investigation. The application is a **detection and decision-support system**, not an inline security appliance.

### In scope
- Secure login and role-based authorization.
- CSV dataset upload, validation, preview, processing, and job status.
- Offline PCAP/PCAPNG analysis through an isolated parser adapter; optional Zeek log ingestion.
- Known-class classification and anomaly/novelty scoring.
- Consistent risk score and severity calculation.
- Alerts, analyst investigation records, analyst feedback, dashboard aggregates, audit logs, and report export.
- Offline evaluation, model metadata, candidate validation, controlled model promotion, and rollback.
- Automated tests, reproducible configuration, and documented local development.

### Out of scope
- Blocking, dropping, injecting, modifying, redirecting, or replaying packets.
- Firewall, IP address, DNS, route, proxy, interface, adapter, or host-network configuration changes.
- Automatic remediation on a host or network device.
- Claims that all unknown attacks will be detected.
- Unreviewed automatic training on production/user feedback.
- Browser-to-MongoDB connections.
- Requiring administrator/root privileges for ordinary operation.

## 2. Product principles

1. **Offline-first:** CSV import and offline artifact analysis are the default workflow.
2. **Passive-only live capture:** if later enabled, it must be explicitly configured, authorized, read-only, and isolated from response actions. Basic features must not depend on live capture.
3. **Fail closed for privileged actions:** unauthorized requests are rejected; model promotion requires an authorized role and a passing evaluation report.
4. **Auditable:** authentication-sensitive actions, dataset processing, feedback, model promotion/rollback, report generation, and simulated response actions create audit events.
5. **Reproducible ML:** preprocessing artifacts, model version, feature schema version, thresholds, and evaluation metadata are versioned together.
6. **No silent contract drift:** API and ML schemas are shared contracts and have contract tests.
7. **Evidence before claims:** no metric or capability is presented as achieved until generated by a recorded test or experiment.

## 3. Technology baseline

- Frontend: React, JavaScript (no TypeScript), Vite, Tailwind CSS, React Router, Axios, Recharts, Lucide React.
- Backend: Python 3.11+, FastAPI, Pydantic v2, Uvicorn.
- Database: MongoDB Atlas via PyMongo only, using a backend repository layer.
- ML: Pandas, NumPy, scikit-learn. XGBoost, PyTorch, and SHAP are optional and require a documented justification.
- Testing: Pytest, React Testing Library, Playwright.
- Artifacts: CSV, PCAP/PCAPNG, optional Zeek logs.
- API serialization: JSON; timestamps are ISO 8601 UTC strings ending in `Z`; IDs are opaque strings.
- Dependency management: Python `pyproject.toml` or pinned requirements; frontend lockfile committed.

### Folder ownership
- `frontend/`: UI and API client only. Must not contain DB credentials, MongoDB drivers, model files, or parsing of untrusted PCAP bytes.
- `backend/app/api/`: HTTP parsing, schema validation, authorization dependencies, and response mapping. Keep business logic in services.
- `backend/app/services/`: application use cases and orchestration. No raw MongoDB queries in route modules.
- `backend/app/repositories/`: all PyMongo operations and DB-specific serialization.
- `backend/app/ingestion/`: safe artifact readers. Parsing libraries are treated as untrusted-input attack surface.
- `ml/src/nids_ml/`: independently importable, deterministic ML code. No FastAPI, PyMongo, HTTP, UI, or application-service imports.
- `docs/`: contract changes and operational instructions.
- `data/` and `ml/artifacts/`: never commit sensitive captures, secrets, user data, or large trained artifacts.

## 5. Module boundaries and dependencies

```text
React UI
  └── HTTP / JSON ──> FastAPI routes
                         └──> Application services
                               ├──> Repositories ──> PyMongo ──> MongoDB Atlas
                               ├──> Ingestion adapters
                               └──> ML public interface ──> nids_ml
```

Allowed dependency direction:
- Routes may import API schemas, dependencies, and services.
- Services may import schemas, repository interfaces, ingestion adapters, and the public ML interface.
- Repositories may import PyMongo and persistence mapping code, but not routes or ML estimators.
- ML code may import its own contracts, NumPy/Pandas/scikit-learn and explicitly approved optional libraries.
- Frontend API modules may import the common HTTP client and frontend types/constants written in JavaScript.
- No circular imports. Use constructor/function injection for service dependencies.
- No network request from ML core; no database query from ML core.

## 6. Roles and permissions

Roles are `admin`, `analyst`, and `viewer`.

| Capability | admin | analyst | viewer |
|---|---:|---:|---:|
| Read dashboard, predictions, alerts | Yes | Yes | Yes |
| Upload and process datasets | Yes | Yes | No |
| Create/update investigation | Yes | Yes | No |
| Submit analyst feedback | Yes | Yes | No |
| Export reports | Yes | Yes | Yes |
| Read model metadata/evaluation | Yes | Yes | Yes |
| Validate candidate model | Yes | No | No |
| Promote/rollback model | Yes | No | No |
| Manage users/roles | Yes | No | No |
| Read audit events | Yes | Limited to own actions | No |
| Execute simulated response action | Yes | Yes | No |

User creation is admin-only after bootstrap. Do not expose public self-registration in v1. A viewer cannot mutate data. The backend must enforce permissions regardless of frontend visibility.

## 7. Core workflows

### 7.1 Authentication
1. Admin bootstraps the first account using a documented one-time script or deployment procedure.
2. User signs in with email and password.
3. Backend verifies a strong password hash and returns a short-lived access token.
4. Frontend sends `Authorization: Bearer <token>`.
5. Logout is client-side token disposal for v1; because access tokens are stateless, immediate revocation is not guaranteed. Use short expiry. Refresh tokens are not part of v1.

### 7.2 Dataset analysis
1. Upload a permitted CSV or supported offline capture/log artifact.
2. Create dataset record with status `uploaded`.
3. Validate file size, extension, parser format, schema, row count, and resource limits.
4. Return validation summary and field mapping errors.
5. Start processing job; status transitions: `uploaded` → `validating` → `ready` or `failed`; processing uses `processing` and ends `completed` or `failed`.
6. Build canonical features, score rows, persist prediction records and alerts in bounded batches.
7. Record dataset/job audit events and model/preprocessing versions.
8. UI polls job status; no promise of real-time processing.

### 7.3 Investigation and feedback
1. Analyst opens an alert/prediction and creates or updates an investigation.
2. Analyst records disposition and notes.
3. Feedback is stored as a separate immutable event, not silently used to retrain a model.
4. Candidate training data is exported/assembled only through a controlled evaluation workflow.

### 7.4 Model lifecycle
1. Train a candidate offline against a versioned dataset and preprocessing pipeline.
2. Evaluate against a defined split and baseline; write a report with metrics and dataset fingerprint.
3. Validate compatibility, schema, integrity, and configured quality gates.
4. Admin promotes the candidate atomically; previous active version remains available for rollback.
5. All promotion/rollback operations are audited. No automatic production retraining in v1.

## 8. REST API baseline

All endpoints use `/api/v1`. Request/response schemas and exact endpoint contracts are in `docs/API_CONTRACT.md`.

- JSON content type: `application/json`, except multipart uploads and binary report downloads.
- Authorization: Bearer access token except health and login.
- Pagination: `limit` default 25, maximum 100; `cursor` is opaque and optional.
- Filtering parameters must be allowlisted and validated; arbitrary MongoDB query expressions are never accepted.
- Errors use `{ "error": { "code": "...", "message": "...", "details": ..., "request_id": "..." } }`.
- No stack traces, secrets, internal paths, raw parser errors, or database exception text in public errors.

## 9. Severity and prediction vocabulary

Canonical prediction fields:
- `prediction_label`: known class label, or `unknown` when no known class is assigned.
- `prediction_type`: `known_attack`, `benign`, `anomaly`, or `uncertain`.
- `confidence`: nullable float in `[0,1]`; calibrated only if calibration has been measured.
- `anomaly_score`: nullable float in `[0,1]`, where higher means more anomalous relative to the fitted detector.
- `risk_score`: integer in `[0,100]`, policy-derived priority score, not a probability.
- `severity`: `critical`, `high`, `medium`, `low`, or `info`.
- `model_version`, `feature_schema_version`, `prediction_timestamp`.

Risk mapping is deterministic and shared across the backend and ML contract:
- 0–19 → `info`
- 20–39 → `low`
- 40–59 → `medium`
- 60–79 → `high`
- 80–100 → `critical`

A separate risk policy may adjust the numeric score using model confidence, anomaly score, attack class, and configured context, but the final score must be clamped to `[0,100]`, explainable by a versioned policy, and mapped through these exact thresholds. Do not represent risk score as a calibrated attack probability.

## 11. Testing strategy

- Unit: validators, schemas, preprocessing, risk mapping, authorization rules, repositories via mocks, parsers, lifecycle gates.
- Contract: OpenAPI schema, request/response examples, error format, enum parity, ML input/output schemas.
- Integration: FastAPI TestClient with a test database or repository fakes; no production Atlas data.
- Frontend: React Testing Library for forms, route guards, loading/error states, charts with empty data.
- End-to-end: Playwright login → upload fixture CSV → validate → process → view predictions/alerts → create investigation → submit feedback → export report → inspect audit event.
- Security/safety: reject oversized/malformed uploads, traversal filenames, unsupported content, unauthorized role actions, dangerous parser options, and all unapproved response actions.
- ML: deterministic fixture tests, leakage checks, feature order, missing values, bounded outputs, serialization round trip, and reproducible evaluation.
- Do not assert invented performance numbers. ML quality thresholds must be configured after a real baseline evaluation and recorded with provenance.

## 12. Definition of done

A feature is done only when:
1. It matches this specification and API/DB/ML contracts.
2. Unit and relevant integration tests pass.
3. Errors use the standard error envelope.
4. Role checks are server-side.
5. User-controlled input is validated and bounded.
6. Audit events exist for sensitive mutations.
7. Logs omit passwords, tokens, secrets, and raw sensitive packet payloads.
8. Documentation and example requests are updated.
9. Frontend and backend run without direct DB coupling.
10. No prohibited host/network action exists.
11. No unverified claim or fake metric is shown in UI or documentation.

## 13. Implementation status reporting

Track every feature as one of:
- `planned`: specified but no code exists.
- `implemented`: code exists but has not passed all acceptance tests.
- `verified`: tests pass in a stated environment and evidence is recorded.
- `deferred`: intentionally postponed, with reason.
- `blocked`: work cannot proceed until a dependency or decision is resolved.

Do not use “complete”, “production-ready”, or “detects unknown attacks” without concrete supporting evidence and a defined scope.
